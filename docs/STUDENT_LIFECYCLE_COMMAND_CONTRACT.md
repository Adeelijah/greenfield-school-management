# Student lifecycle command foundation (Step 496)

`src/lib/students/lifecycle-commands.ts` is pure application logic. It does not import a database client, Supabase client, Next.js handler, or UI component with side effects. It returns a plan; no effect is executed. Approved preview components remain unchanged.

## Commands and results

The discriminated `LifecycleCommand` union covers initial enrollment/class placement, academic decision proposal and finalization (promote, repeat, graduate), transfer, early exit, and re-admission. A success is either a new `LifecyclePlan` or an idempotent replay with an existing operation ID. Failure has a stable code and a safe message. Proposals contain no audit event or enrollment write. Each finalized plan contains a structured audit contract and effects that must be applied together.

The command deliberately has no school ID, role, or assignment field. Runtime checks reject extra claims with those names. `VerifiedLifecycleContext` must be assembled **only by a trusted server adapter** after verifying the auth user, exactly one active school membership, and (for a teacher) school/membership/class/session assignment rows. The pure function cannot verify the provenance of an object supplied to it. It matches an active assignment to the source enrollment and compares every snapshot row's school ID and student ID with the verified context, then uses the Step 494 role matrix through `canPerformLifecycleOperation`. Admins can enroll, finalize, depart, or re-admit; teachers can only propose for an assigned enrollment; bursars have no lifecycle operation. No browser request may construct `VerifiedLifecycleContext` directly.

The snapshot includes school structure, classes, sessions, one student and all of that student's enrollment, decision, departure, readmission and idempotency history. A future adapter must load this from authoritative school-scoped rows, not from client JSON. The command layer reuses the approved `validateClassStructure`, `validateClassAssignment`, `validateAcademicDecision`, `sessionYear` and `validateStudentExit` functions. It additionally requires contiguous Primary 1 through the configured Primary 5/6 final level, resolves classes to independent level/section IDs, rejects duplicate session placement and pending/final outcome conflicts, and checks student status transitions. Re-admission preserves departure and enrollment history; it plans a new enrollment and a linked readmission.

## Future adapter and atomicity contract

`LifecyclePersistenceAdapter.withStudentTransaction` and `LifecycleTransactionPort` are type-only contracts. A future server handler must parse/whitelist untrusted input, resolve verified membership, open a transaction, acquire locks in the plan's order (school structure, student, source enrollment), load a complete scoped snapshot, call `decideLifecycleCommand`, and apply a new plan atomically. It must recheck the expected structure and student versions, current enrollment, assignment (for teacher proposals), proposal state, duplicate destination session, departure/readmission state and idempotency key inside that transaction. Store the plan's canonical SHA-256 fingerprint with the key; an identical retry returns the original operation, and different content with the same key fails. Unique/FK constraints remain the race backstop. Return no effects on replay.

For a final operation, apply all effects, idempotency record and audit event in one transaction; if any fails, roll back. The audit contract contains school, verified actor membership/role, request ID, action, student/source IDs and old/new status codes. It contains no names, contacts, notes, raw request body or credential. The adapter must assign IDs and timestamps from trusted server/database sources. A teacher proposal stores a proposal only; admin finalization reloads and revalidates it before applying.

`close_source_enrollment` is intentionally a semantic effect rather than a database status value. The existing enrollment enum has only `active`, `graduated` and `withdrawn`, so a historical `completed` state and its migration require a separate decision. The Step 494 draft also lacks a student version column and a cross-table idempotency namespace. These are blockers to a real adapter, not invitations to repurpose `withdrawn` or start persistence now. The draft permits a new departure after a later re-admission from a different enrollment; that product rule needs approval.

## In-memory transaction simulation

`src/lib/students/lifecycle-memory-adapter.ts` implements the port only for fictional, process-local data. Its seed includes two schools, memberships, class/session assignments, students, enrollments, decisions, departures, readmissions, idempotency records and audit events. The simulator derives role and assignment rows from its own cloned store, never from command fields. It serializes transactions with one coarse in-memory queue, loads a school-scoped snapshot, calls the pure planner, and applies effects to a private clone. The clone is published only after all effects, audit and idempotency recording succeed. Injected effect, audit and idempotency failures discard the entire clone. A matching retry returns the same operation ID without new effects; changed content with the same key fails. Optimistic version checks and the queue make conflicting outcomes deterministic in tests. This is a simulation of transaction behavior, not a claim that PostgreSQL lock ordering or isolation levels have been tested.

The fake maps `close_source_enrollment` to an in-memory `completed` status and preserves old enrollment/departure rows through re-admission. The existing Drizzle `enrollment_status` enum does **not** contain `completed`; the Step 494 SQL draft does not add it. `students.version` is also absent from that draft. The fake has a school-wide idempotency list, while the Step 494 proposal puts separate unique keys on decision/departure/readmission tables and none on an initial enrollment command. The fake links an audit entry to a generated operation ID, but the proposed audit table has no operation ID column or immutable enforcement. These mismatches must be resolved in a reviewed forward-only design before a PostgreSQL adapter is possible.

A future PostgreSQL implementation of the port must derive school/role/assignment from verified authentication; use one transaction for snapshot load, planning, effects, audit and idempotency; acquire locks in the documented order; compare student/structure versions; enforce school-scoped FKs and destination uniqueness; and return the stored operation ID on replay. The simulator's global queue is intentionally simpler than database row locks. Its public `execute` accepts a fictional identity token for tests and is **not** an authentication mechanism.

## Offline limits

The tests use fictional students and in-memory snapshots. They verify pure decisions, plan shape and in-process atomic simulation, not SQL syntax, Drizzle migration compatibility, PostgreSQL transactions, RLS, grants, deployed auth, concurrency under real database locks, or browser behavior. Step 494 DDL and RLS files remain unexecuted drafts. No database handler is wired.
