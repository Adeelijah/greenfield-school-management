# Staging domain and installation review

This milestone prepares dormant public-schema domain adapters, a verified server command factory and an offline installation-review builder. Nothing installs SQL, opens a connection, enables a route or changes live authentication. The previously supplied 540-test offline result is verified; new results below are separate.

## Shared domain logic

`report-card-sql-scope.ts` issues immutable namespace configurations. Existing fixture APIs continue to reject `public` and arbitrary schemas before authentication or SQL. Shared reader/writer cores accept only issued objects; copied or deserialized shapes fail. A staging scope requires the explicit isolated-staging mode, fixed school UUID and exact login/execution role names. Scope configuration is not identity proof.

Public domain operations verify the actual login/execution identities, take the shared source gate before complete actor discovery, and compare complete authority with the subsequently mapped user, membership, school, role and final Primary year. RLS-filtered membership rows cannot replace the complete lookup. The shared cores retain existing source recalculation, assignment checks, optimistic versions, action-family fingerprints, historical replay and atomic snapshot/release/audit/receipt rules. Withdrawal continues to permit stale academic sources while requiring current administrator authority.

`createVerifiedStagingReportCommands` owns the SDK identity bridge and closed request parser. It captures explicit configuration and uses the role adapter and complete staging boundary around the actual seven action adapters. A common scalar response decoder runs inside the outer transaction, so failed or malformed outcomes cannot commit. There is no caller-supplied identity callback, environment discovery, application database fallback or route import. Consumers must use this server factory rather than treating a scope object as authenticated authority.

## Installation-review assembly

`buildStagingReportInstallationReview(config)` reads only the fixed repository dependency and coordinated-guard drafts and the actual explicit staging metadata assembly. Its independent proposal emitter selects sixteen new tables and four enums, emits tables/indexes before cyclic foreign keys, and rejects unsupported metadata. It does not invoke the disposable fixture generator, create base tables or become a Drizzle Kit entrypoint. Metadata tests compare its output against the existing semantic fixture evidence as an independent regression oracle.

The pure composer requires the explicit `reconciled-semantic-0000` baseline declaration, fixed school and source commit. It places dependencies, proposals, coordinated guards and the fixed-school policy fragment inside one transaction. Runtime helper grants and SET-only membership activation follow the coordinated guard revocations. A frozen manifest hashes every phase and the final SQL. These hashes identify supplied source bytes; they do not verify a Git checkout, installed catalog or authorization to execute. The fixed-input builder is the review assembly surface; the lower-level composer accepts trusted review material only.

This is an additive candidate for a separately reconciled semantic baseline, not a general migration/repair tool. It does not backfill legacy classes, choose the school's final Primary year, apply unknown partial installations, change the journal, grant academic source-writing privileges or maintain revision-claim retention. The target must already provide the reviewed Supabase auth functions/roles and strictly configured `greenfield_app` login. Effective PUBLIC/default/transitive privileges, private function ownership, trigger bodies, policy interactions and rollback/recovery must be inspected before any installation authorization.
